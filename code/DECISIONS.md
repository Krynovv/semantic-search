## 1. Способ загрузки датасета CodeSearchNet

**Решение.** `load_dataset("code-search-net/code_search_net", "python")` из `datasets 5.2.0`.
Ветка `loader="parquet"` (прямое чтение `python/{train,validation,test}-00000-of-00001.parquet`
через `hf://datasets/...`) оставлена как запасной вариант, переключение — флаг `--loader`.

**Проверено фактически.** Локальный прогон 2026-11-15: hub-загрузка отработала успешно
(в репозитории датасета лежат parquet-файлы, `datasets` сам их подхватил и сгенерировал
сплиты; `train` ≈ 412k, `validation` ≈ 23k, `test` ≈ 22k строк). Loading script в
`datasets ≥ 3.0` не поддерживается, но он и не нужен: данные доступны в parquet.

**Почему так.** Требование плана — проверить, работает ли loading script в выбранной
версии `datasets`, и записать результат. Ответ: не работает (скриптов нет), parquet
работает, а `load_dataset` в этой версии сам выбирает parquet.

**Отвергли.** Скачивание и разбор parquet вручную (`pyarrow.read_table`) — лишний код:
`datasets` умеет то же самое.

## 2. Что считается «запросом»

**Решение.** Запрос = **первый абзац** docstring (текст до первой пустой строки),
после `inspect.cleandoc` (снимается общий отступ), слова склеены в одну строку,
длина ограничена **30 словами**. Требование «docstring ≥ 3 слов» проверяется и по
полному docstring, и по извлечённому запросу.

**Почему.** Первый абзац docstring — это то, что человек обычно пишет как «что делает
функция»; хвост docstring часто содержит примеры, детали и ссылки, которые только
разбавляют запрос. Ограничение в 30 слов нужно, чтобы запрос оставался коротким
и чтобы дедупликация по нормализованному запросу не склеивала разные по смыслу
запросы в один.

**Отвергли.** Взять весь docstring (тогда запрос смешивается с примерами кода);
взять только первую строку (теряется контекст: `"""Get info about the node."""`).

## 3. Как удаляется docstring из кода

**Решение.** Через модуль `ast`: у функции берётся первый строковый литерал тела
(`body[0]` — `ast.Expr` со `str`-константой) и **вырезается по байтовым смещениям**
(`lineno`/`col_offset`/`end_lineno`/`end_col_offset` в коде, переведённом в UTF-8
байты). `ast.unparse` **не** используется: он переформатирует код, теряет комментарии
и переписывает тело функции. Число строк сохраняется (вырезается ровно столько же
переводов строк, сколько было внутри docstring), поэтому номера строк в `code`
совпадают с исходными. Если тело функции состояло **только** из docstring, на его
место ставится `pass` — иначе получился бы невалидный Python. Если код не
разбирается `ast.parse` — пример пропускается (счётчик `unparsable_code`).

**Почему.** Требование плана: без удаления docstring запрос буквально содержится в
документе и метрики бессмысленны. Байтовые смещения вместо символьных — потому что
`ast.col_offset` в CPython считается в **байтах** UTF-8, а не в символах.

**Отвергли.** `ast.unparse` (теряет комментарии и форматирование); удаление
docstring регулярными выражениями (ломается на вложенных кавычках и префиксах `r`,
`f`, `b`); `inspect.getdoc` + пересборка функции (переписывает код целиком).

## 4. Фильтр «код длиннее 512 токенов»

**Решение.** Токенизатор `intfloat/multilingual-e5-base` (та же модель, что будет
использоваться в Шаге 2), измеряется **код без docstring** — то есть ровно тот текст,
который будет индексироваться. Ограничение — 512 токенов (максимальная длина
контекста модели).

**Почему.** Считать токены исходного кода с docstring означало бы отсекать примеры,
которые после удаления docstring влезли бы в модель.

## 5. Дедупликация

**Решение.** Два ключа: **нормализованный код** (нижний регистр + схлопнутые пробелы) и
**нормализованный запрос** (нижний регистр, без пунктуации, схлопнутые пробелы).
Дедупликация **глобальная по всем сплитам** (train → validation → test), первый
выигравший остаётся.

**Почему.** Требование «у каждого запроса ровно один правильный ответ» и запрет
пересечений сплитов. Если дедуплицировать только внутри сплита, один и тот же запрос
(одинаковый docstring у разных функций) окажется и в train, и в test — это утечка.
Побочный эффект: в корпус кандидатов попадают только функции с уникальным запросом,
то есть для любого запроса из теста ровно одна функция в корпусе является верным
ответом.

**Отвергли.** Дедупликацию только по коду (тогда запрос может соответствовать двум
разным функциям); дедупликацию внутри сплита (утечка между сплитами).

## 6. Состав сплитов

**Решение.** Используются официальные сплиты CodeSearchNet. Корпус кандидатов:
val — 5000 функций, test — 5000 функций; запросы для оценки берутся **из этого
же корпуса** (val — 2000, test — 1000). Размер корпуса и число запросов —
константы `DataConfig` (`val_pool_size`, `test_pool_size`, `val_queries`,
`test_queries`, `train_size`).

**Почему.** Требование плана: фиксированный корпус кандидатов N = 5000 и 1000 запросов
из него. Запросы из корпуса — иначе правильный ответ может лежать вне корпуса
и Recall@k невозможно интерпретировать.

**Проверено фактически (2026-11-15).** Официальные сплиты CodeSearchNet разделены
**по репозиторию**: общих репозиториев между train (12 231), validation (679) и test (680)
нет ни одной пары. Поэтому утечки на уровне проекта не бывает, а дополнительно
исключать функции по репозиторию не нужно.

## 7. Модели перевода

**Решение.** `Helsinki-NLP/opus-mt-en-ru` (EN→RU) и `Helsinki-NLP/opus-mt-ru-en` (RU→EN).
Обе доступны на HuggingFace (проверено через API 2026-11-15), лицензия apache-2.0,
формат Marian, токенизация через `sacremoses` + `sentencepiece`.

**Почему.** План предлагает opus-mt или NLLB. NLLB (facebook/nllb-200-distilled-600M)
в 3–4 раза тяжелее и медленнее, а для docstring коротких строк opus-mt даёт
сопоставимое качество (проверяется выборкой `translation_sample.csv`, оценку ставит
человек). Локальная модель — не требует API-ключа.

**Отвергли.** NLLB-200 (избыточный вес для коротких docstring); перевод через API-LLM
(нужен ключ, воспроизводимость хуже, появляется зависимость от внешнего сервиса).

**Пересмотрено (см. §11).** Оценка opus-mt оказалась низкой (2,62 из 5), поэтому
выбор переводчика решили проверить слепым сравнением opus-mt против NLLB-600M
на тех же 100 запросах, а не по умолчанию оставить opus-mt.

## 8. Круговой перевод и его влияние на выводы

**Решение (и предупреждение).** Последовательность EN→RU→EN — **круговой перевод**.
Если BM25 получает запрос, переведённый обратно из машинного русского перевода,
то лексическое совпадение с исходным английским запросом искусственно завышено:
переводчик сохраняет термины и порядок слов лучше, чем это делает независимый
русскоязычный запрос. Поэтому:

- метрику «BM25 по RU→EN» на машинно переведённых запросах считаем **верхней
  оценкой**, а не честным измерением;
- выводы о том, помогает ли гибрид (dense + BM25), делаем **по ручным запросам**,
  где перевода нет вообще;
- дополнительно сравниваем BM25(исходный EN) и BM25(RU→EN) на одном и том же тесте,
  чтобы увидеть величину завышения.

**Почему.** Это следствие дизайна теста, а не ошибка данных, но без оговорки он
приведёт к завышенной оценке BM25 в итоговой таблице.

**Решение.** Корень данных/кэша/моделей — переменная окружения `SEMSEARCH_HOME`
(по умолчанию `kursovaya-tex/code/var`, вне git). Пути внутри кода — только `pathlib`.
Виртуальное окружение — `uv venv --python 3.12 .venv` внутри `kursovaya-tex/code/`,
пакеты ставятся только туда. Версии зафиксированы в `requirements.txt`.

**Почему.** Требование плана: без хардкода `/home/...` и `/content/...`, pip в
системный Python запрещён (PEP 668), torch/faiss на системном Python Arch не ставятся.

## 11. Слепое сравнение переводчиков (opus-mt против NLLB)

**Решение.** Сравнение opus-mt-en-ru и `facebook/nllb-200-distilled-600M` проведено
**вслепую** на тех же 100 запросах, что и `results/translation_sample.csv`.
В `results/translation_blind.csv` для каждого запроса стоят два перевода
(opus-mt и NLLB) в колонках `variant_a` / `variant_b`, причём в `variant_a`
попадает то opus-mt, то NLLB — по `random.Random(42)`, для каждой строки отдельно
(вероятность 0,5). Соответствие сохранено в **отдельном** файле
`results/translation_blind_key.csv` (id, a_is). Оценщик проставляет оценки 1–5
в колонки `rating_a` / `rating_b`; ключ открывается только после заполнения оценок.
Сведение — `python -m semsearch.data.blind score`: средние баллы, распределение 1–5
для каждого переводчика, число строк «NLLB лучше / хуже / равно» и p-значение
точного двустороннего **теста знаков** (биномиальная сумма считается вручную:
scipy в окружении нет; Уилкоксон с нулевыми ранговыми суммами даёт тот же ответ).

**Почему.** Открытая оценка переводов не сравнивает переводчики, а сравнивает
переводчик «с подписью»: оценщик видит, где opus-mt, и это смещает оценку в его
пользу. Слепой порядок убирает подсказку, а отдельный ключ не даёт восстановить
соответствие до конца оценки (и позволяет пересобрать файл с тем же seed — 42).
Перевод NLLB сделан на том же CPU и с теми же `beams=4`, иначе сравнение было бы
нечестным; ключ кэша переводов включает имя модели, поэтому переводы opus-mt и NLLB
не смешиваются.

**Почему NLLB-600M, а не 1.3B/3.3B.** Это та же архитектура и то же семейство
моделей, но весит меньше (2,5 ГБ против 5+ ГБ) и переводится на CPU за разумное
время; вопрос «какой переводчик лучше» решается слепым сравнением, а не
закладкой в вес модели. Лицензия NLLB — cc-by-nc-4.0 (некоммерческая),
для учебной курсовой это допустимо, для промышленного применения — нет.

**Отвергли.** Открытое сравнение (видно, где какой перевод); оценку по BLEU/chrF
вместо человеческой (на коротких docstring с терминами автоматические метрики
плохо отражают «понятен ли перевод человеку», а человеческая оценка уже есть);
третий вариант — перевод через LLM-API (платно, ключ не подтверждён, оставлен
на следующую итерацию, если NLLB не покажет выигрыша).
