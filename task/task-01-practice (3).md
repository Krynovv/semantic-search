## Новизна (фиксирована, не менять без согласования)
1. Собственный русскоязычный датасет пар «запрос на русском → функция на Python» (перевод описаний CodeSearchNet + ручная выборка реальных запросов).
2. Дообучение мультиязычной модели эмбеддингов под кросс-языковой поиск RU-запрос → код.
3. Кросс-языковое гибридное ранжирование: векторный поиск по исходному RU-запросу + BM25 по запросу, машинно переведённому RU→EN; объединение через Reciprocal Rank Fusion (RRF); экспериментальное сравнение с базовыми вариантами и абляция (где гибрид помогает, а где нет — отрицательный результат тоже фиксируется).

## Стек
- Python 3.11+, строгие type hints, `ruff` + `mypy`.
- `sentence-transformers`, `transformers`, `torch`, `datasets`.
- `faiss-cpu` (векторный индекс), `rank_bm25` (лексический).

- Обучение: ноутбук для Google Colab (GPU T4/L4) или Kaggle.
- Секреты (API-ключи, если переводим через LLM) — только через `.env`, файл в `.gitignore`, есть `.env.example`.

## Шаги

### Шаг 1. Данные
- Загрузить CodeSearchNet, подмножество Python (через HF `datasets`; проверить актуальное имя датасета на Hugging Face).
- Очистка: убрать функции без docstring, docstring < 3 слов, код > 512 токенов, дубликаты (по нормализованному коду).
- Взять первую строку/абзац docstring как «запрос».
- **Удалить docstring из кода** (через AST: убрать первый строковый литерал тела функции; при ошибке парсинга — пропустить пример). Без этого запрос буквально содержится в документе и метрики бессмысленны. Применяется и к обучению, и к оценке. Проверка: тест, что ни один `code` в train/val/test не содержит свой `query` как подстроку.
- Дедупликация по нормализованному запросу (lowercase, без пунктуации): у каждого запроса ровно один правильный ответ.
- Сплиты: использовать официальные сплиты CodeSearchNet; train ~50–100k пар, val ~2k запросов, test: **фиксированный корпус кандидатов N = 5000 функций** и 1000 запросов из него. Размер корпуса — константа в конфиге, указывается в записке. Проверить отсутствие пересечений между сплитами.
- Загрузка датасета: проверить при установке, работает ли загрузка через loading script в выбранной версии `datasets`; если нет — брать parquet-версию. Результат записать в `DECISIONS.md`.
- Перевод запросов на русский (`translate.py`): основной вариант — локальная модель (`Helsinki-NLP/opus-mt-en-ru` или NLLB) на GPU; альтернатива — LLM через API (ключ из `.env`). Пакетная обработка, кэширование результатов на диск, возобновление после обрыва.
- Ручная проверка качества: выгрузить 100 случайных переводов в `results/translation_sample.csv` (оценку делает человек).
- Дополнительный тест «реальные запросы»: файл `data/manual_queries.jsonl` (цель — 100, минимум 50 запросов на русском, написанных вручную, + id правильной функции из test-корпуса) — шаблон и 10 примеров создаёт worker, остальное дополнит автор.
- Обратный перевод для BM25: функция перевода RU→EN для запросов (та же схема — локальная модель `opus-mt-ru-en`/NLLB, кэш на диск).

### Шаг 2. Базовые варианты (baseline)
- B1: BM25 по коду (с разбиением идентификаторов) — для EN-запросов, для RU-запросов как есть (ожидаемо ≈0, это нижняя граница) и для RU-запросов, переведённых RU→EN.
- B2: предобученная мультиязычная модель без дообучения. Основной кандидат — `intfloat/multilingual-e5-base` (учесть префиксы `query: ` / `passage: `). Проверить актуальность/доступность модели на HF перед использованием.
- Посчитать метрики на test (EN-запросы и RU-запросы отдельно) → `results/baselines.csv`.

### Шаг 3. Дообучение
- `MultipleNegativesRankingLoss` (in-batch negatives), пары (ru_query, code). Батч-семплер без дубликатов (`BatchSamplers.NO_DUPLICATES` в sentence-transformers — проверить наличие в установленной версии).
- Эксперименты (минимум 2): (а) только RU-пары; (б) смесь RU + EN пар — как способ снизить забывание английского. Для каждого — метрики на EN и RU **до и после** дообучения.
- Конфигурация через dataclass: lr, batch size, epochs, max_seq_length, warmup; seed фиксирован.
- Чекпоинты каждые N шагов (Colab может оборвать сессию), возобновление с чекпоинта.
- Логирование loss и val-метрик по эпохам → `results/train_log.csv` + график `results/loss.png`.
- Модель сохранять в `models/` (в `.gitignore`), путь — через конфиг.

### Шаг 4. Гибридный поиск
- `fusion.py`: RRF, `score(d) = Σ 1 / (k + rank_i(d))`, k=60 по умолчанию, параметризуемо.
- Подобрать k (и вес, если линейная комбинация) на val, не на test.
- Итоговая таблица сравнения на test → `results/final_comparison.csv`:
  BM25 | модель без дообучения | дообученная (а) | дообученная (б) | гибрид (BM25 по RU→EN + лучшая дообученная).
  Отдельно для: EN-запросы, RU-запросы (перевод), RU-запросы (ручные).
- Для каждой метрики — 95% bootstrap-доверительный интервал (1000 ресэмплов по запросам, фиксированный seed). Для ручных запросов в отчёте явно указать, различимы ли конфигурации статистически.
- В отчёте и `results/` указать размер корпуса кандидатов и число запросов.

### Шаг 5. Индексация реального репозитория + CLI
- `cli.py index <path>` — рекурсивный обход .py, пропуск `venv`, `.git`, `node_modules`, бинарей; файлы с ошибками синтаксиса логируются и пропускаются (не валят индексацию).
- `cli.py search "<запрос>" -k 10` — вывод: score, путь, имя функции, строки, первые строки кода.
- Индекс сохраняется на диск и загружается без пересчёта.
- Флаг `--keep-docstrings` (по умолчанию выкл., как при оценке): в реальном репозитории docstring можно оставлять — это отдельный режим, его эффект показать в demo_queries.md, но не смешивать с метриками.
- Демонстрация на 1–2 открытых репозиториях → примеры выдачи в `results/demo_queries.md`.

### Шаг 6. Тесты (контрольная точка)
Тесты пишутся **вместе с модулем** на каждом шаге (fusion и metrics — сразу при создании); Шаг 6 — финальная проверка полноты и покрытия. Обязательный минимум:
- `data`: удаление docstring из кода; отсутствие query в code; отсутствие пересечений сплитов.
- `parsing`: функции, методы классов, вложенные функции, декораторы, async def, файл с синтаксической ошибкой, пустой файл.
- `fusion`: корректность RRF на ручном примере, пустые списки, документ только в одном списке.
- `metrics`: MRR/Recall на ручных примерах с известным ответом.
- `index_dense`/`index_lexical`: build → save → load → тот же результат.
- `searcher`: пустой запрос / k > размера индекса / пустой индекс — явные ошибки или пустой результат, без падения.

## Граничные случаи (обязательно обработать)
- Пустой/из пробелов запрос → `ValueError` с понятным сообщением.
- Код не в UTF-8 → пробовать с `errors="replace"`, логировать.
- Очень длинные функции → усечение до max_seq_length модели (с логом), а не падение.
- Путь к репозиторию не существует / не директория → понятная ошибка CLI.
- Обрыв сессии Colab при обучении и переводе → возобновление с кэша/чекпоинта.
